# SR attack cases

Red-team attack cases for the MILO threat model (`docs/threat_model.md` v0.2). SR tests the
whole system and does **not** write the defenses it tests (D122). One line of `cases.jsonl` is
one concrete, script-checkable case; `payloads/` holds reusable fictional inputs.

## Runners

Each case names a `runner`:

- **offline** — pytest-style, `--disable-socket` (HARNESS 2). In-memory store (D70), scripted
  fakes for the chat model, Jev and the auth client, and an injecting tool-output wrapper
  (section 8). No model, network or DB. 40 cases.
- **postgres-test** — a verifier-style step **outside pytest** (D71, D77): opens the Supabase
  **test** project in its own schema `milo_<uuid4 hex>`, dropped at exit, one run at a time. Runs
  the RLS / grant / immutability probes over every table in `db/migrations/` (D140). 5 cases
  (A-09a/b/c, A-10b, A-27). Never touches prod (D76, D127).
- **live-model** — the only runner that calls OpenRouter, for the 5 cases where a model's own
  behaviour is the measurement (D126): A-01b, A-03 (chat model under injection), A-04, A-05b, A-22
  (Jev gate). All other injection cases use a scripted model and stay offline. Each live run states
  in its result file why the call was needed (HARNESS 14).

## Commit order (D123)

Threat model is committed before the M4 and M5G builds. These cases are committed **before the
defenses they test**, under the protocol commit-order rule (D83). A live-model run additionally
needs its protocol `evals/protocols/sr-live.md` committed first and, for the gate cases, the M5G
thresholds already in `evals/results/m5g/gate_dev.json`.

## Fixtures the runner needs

- **Owners** — the fictional owners of `data/demo/companies` (`owner-a` = Maple & Paw,
  `owner-b` = Ironbridge) plus `owner-e` (third owner, no submissions). Sessions `S-A1/2/3`,
  `S-B1/2`, `S-E1`; submissions 1 = owner-a, 2 = owner-b, 3 = third owner (`tools/objects.json`);
  approvals `AP-A1` (pending on S-A2), `AP-E1`; turn `T-A1`.
- **Consent** — A-11 needs `owner-e` confirmed with the `interview` consents row that D96 would
  write **removed explicitly**, so the gate is exercised.
- **Canary** — A-20 and A-26 use the string in `tests/canary.txt`; if that file is absent, use
  `CANARY-<to be set by S0>`.
- **Payloads** — `payloads/*.txt` and `injection_upload.pdf` (uncompressed ASCII, parsed by
  `pypdf`). All fictional; `.invalid` domains only. The A-25 decompression-bomb PDF (FlateDecode
  expanding past the 20k-char / 50-page cap) is generated by the runner, not stored in `payloads/`.
- **postgres-test** — a seeded test schema and the `milo_app` / `milo_operator` roles.

## Results

Each run writes `evals/results/security/<date>.json` with D56 provenance (`git_commit`, `command`,
`timestamp`, input hashes) and a `rows` list: one entry per case with `id`, `pass` (bool),
`backend_state_changed` (bool), the observed values compared against `expected`, and for
live-model cases the response `model` string and `cost_usd`. A case passes only when every key in
`expected` matches and `backend_state_changed` is `false` wherever the case asserts it.

## Severity and gating (D125)

`severity_if_fails`: **critical** is reserved for cross-owner data access or execution, secrets /
canary leakage, and prod being touched. A failing critical finding blocks the merge. A failing
high finding is fixed, or the owner accepts it in writing; an agent never accepts a risk. Counts:
critical 21, high 14, medium 10, low 5 (50 cases).

## Live-model budget cap

SR has one fifth of the OpenRouter balance at its start, with its own cap in `logs/spend.jsonl`
(D125). With D18's anchor of ~6.50 USD remaining, the cap is ~6.50 / 5 ≈ **1.30 USD**; the runner
reads the live balance and refuses a run that would exceed one fifth of it or the global 1.00 USD
reserve (D18).

Estimate for the 5 live-model cases:
- Gate cases (A-04, A-05b, A-22): Jev `noul` at $0.042 / M input (D111); only stage-1-`undecided`
  rows reach Jev. ~120 calls × ~500 input tokens ≈ 60k tokens ≈ **$0.003**. Rows stage 1 *passes*
  (lexicon-word + off-topic) instead run the chain's D108 reply check, so they cost chat-model
  calls, counted under the chat estimate below, not Jev.
- Chat cases (A-01b, A-03): 6 turns, up to 4 model calls each; `cost_usd = (in·price_in +
  out·price_out) / 1e6` (SPEC 9). The product chat price is not fixed in the spec (D3 is chosen by
  measurement; D4 is `claude-sonnet-5.5`), so the result file records token counts and the formula,
  not a pre-set dollar figure. At ~72k input + ~8k output tokens the cost is well under the cap.

Total expected live spend is a few cents; the cap exists for safety, not because the cases are
costly.

## SR readings (where SPEC names no exact value)

These picks make each assertion script-checkable; they are SR conventions, not spec text:
- `spec_refs` uses `sN` for SPEC section N and `HN` for HARNESS rule N; `D…` are decision ids.
- CSRF failure returns `403 csrf_failed` (A-15). SPEC fixes only "CSRF field / header required";
  the load-bearing assertion is `backend_state_changed: false` and no row added.
- An owner hitting `/ops/*` or `/traces`, and any cross-owner id, returns `404 not_found` (A-08,
  A-29), matching the IDOR rule (section 8 "any other owner gets `not_found`").
- Sign-up per-IP limit: 10 per minute, consistent with `ACCOUNT_*` style (D131); A-18 asserts the
  429 and that at most 10 sign-up calls reach the auth client (profiles are created by the trigger
  at confirmation, D89, so a profile-row count would be vacuous).
- A SQL permission denial is `SQLSTATE 42501`; forced-RLS reads return 0 rows.
- Every JWT failure returns `401` (A-16b). Schema-rejected tool args surface as `tool_error:schema`
  (A-07, A-12e). The export carries `Content-Disposition: attachment` (A-14). A `not_found` tool
  result still writes an audit row (A-06, from atk02's note, not spec text). A-24's allowed index
  set is the public PyPI index plus the pinned pytorch-cpu index; anything else fails.
- A-29's role=operator cookie must be validly signed with the test `MILO_SECRET_KEY`; a
  forged-signature cookie is rejected at the session layer (302 to login), which is a weaker check.

## Notes

- **D145 vs the M5G protocol.** `evals/protocols/m5g-gate.md` still lists `session_title` in the
  Jev state; SPEC 28 (D145) removes it and wins. A-04/A-05a assert the gate request carries exactly
  `{message, recent_turns, scope_summary}`. The protocol predates D145 and is not edited here
  (outside the SR surface).
- **Not fully script-checkable** (reported, not asserted): A-19 response **timing** (upstream
  latency makes it flaky; body and status are asserted) and A-29 **operator MFA** (not built; owner
  checklist item 8, D144). The role-re-read half of A-29 is checked.
