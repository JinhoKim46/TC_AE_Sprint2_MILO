### The open point: Supabase tokens in the session cookie (D136)

**What is there.** With `SupabaseAccounts` the Flask session cookie holds `{"auth": {"a": <access JWT>, "r": <refresh token>}, "csrf": ...}`. Flask's cookie is signed with `MILO_SECRET_KEY`, not encrypted: the runner decodes it without the key and reads both tokens. The cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, and production adds HSTS.

**Risk.** Anyone who obtains the cookie value (from the browser's cookie store on a shared or compromised device, a proxy or load-balancer log that records `Cookie` headers, a crash report or a pasted debug dump) gets the raw Supabase refresh token. Two consequences go beyond what the owner accepted in section 18 item 9:

1. Item 9 accepts a stolen *access* token, valid for at most one hour. The refresh token mints new access tokens for as long as the Supabase session lives, so the window is the session's lifetime, not one hour.
2. The tokens work against the Supabase Auth API directly, outside MILO's controls (no MILO rate limit, no MILO audit). For example, they can change the account's email, and its password unless the project requires reauthentication for password changes. That turns a stolen session into account takeover.

Sign-out limits the damage: `SupabaseAccounts.logout` calls Supabase `/logout?scope=local`, which revokes that session's refresh tokens. The access JWT stays valid until it expires (verified locally, D88). That residual is the one already accepted, and the runner shows it: the replayed cookie is accepted after sign-out. Note that D136 speaks of "the Flask session and the stored refresh token" as two separate things, which assumes a store outside the cookie.

**Severity (D125).** Likelihood: low. HttpOnly plus a strict CSP and escaping (A-13a, browser check) close the XSS route, and Secure plus HSTS close the network route, so the cookie has to be stolen at rest or from logs. Impact: high (takeover of one owner account and its company data until sign-out). T-15's own row rates medium likelihood and high impact. **Overall: medium.** It is not a failure of any written case: A-16a's flags and rotation pass, and D136's literal requirements are met. It does widen the accepted residual, so before production either the fix below lands, or the owner extends section 18 item 9 in writing to cover the refresh token (D125: an agent never accepts a risk).

**Smallest fix** (not implemented):

- *Smallest change, restores confidentiality only:* encrypt the `auth` value inside the cookie, for example AES-GCM or Fernet from `cryptography` (already in `uv.lock`), with a key derived from `MILO_SECRET_KEY` by HKDF under its own label. This touches about 20 lines in `routes.py` (`regenerate_session` and `gate`). A stolen cookie then still replays to MILO, but it no longer exposes tokens for direct Supabase use or in logs. It gives no revocation.
- *Recommended, also closes item 9 inside MILO:* keep the tokens server-side, keyed by a random 256-bit session id. The cookie holds only that id, and sign-out deletes the row, so a replayed cookie dies at once. This needs a `web_sessions` table with RLS (an M5-store migration with its D140 test). An in-process dict works for the single-worker dev and test setup only.
