## Verdict: FAIL

The M4 done-line passes in full and every hard rule holds. The verdict is FAIL because two SR cases on the approval path the M4 measurement itself uses (`App.resume_approval`) show a tool execution the case says must not happen:

- **A-12b (high).** Two concurrent `resume_approval` calls on one pending approval ran `withdraw_submission` twice (and made two follow-up model calls) when both callers read `pending` before either wrote. `App.resume_approval` (`src/milo/app.py:189-212`) reads the row, then sets `approved`, with no lock and no compare-and-set. The compare-and-set of fix cycle 1 lives in `ApprovalService.resolve` (`src/milo/tools/approvals.py:73-116`), which nothing under `src/` calls; the attack runner's auto-approve arm (`evals/agent/run_attacks.py:380`) and the SR cases go through `App.resume_approval`. In 300 natural two-thread trials the race did not surface (GIL scheduling); the forced interleaving reproduces it deterministically. The second execution returned `already_withdrawn`, so the state damage is nil for this tool; the finding is the missing guarantee of SPEC section 8 step 2 ("the tool runs once"). In discovery mode the store is the Postgres `approvals` table (section 8 step 1), so the read-then-write window is a real round-trip, not a contract-mode artefact. The threat model assigns T-11 to M5b (lifecycle) and M3 (backend); the integrator routes the fix knowingly.
- **A-12d (high).** `App.resume_approval` does not recheck `args_hash` before calling the tool (`app.py:207-209`): with the stored args tampered to `{submission_id: 2}`, it executed the tampered call, and only the owner filter (`not_found`, D65) kept owner-b's row unchanged. The case allows only a hash refusal or execution with the bound args. `ApprovalService.resolve` refuses on the hash mismatch (`approvals.py:107`).

Both findings sit in `src/milo/app.py`, which is integrator-owned (Appendix A). The M4 builder delivered the guarded resolver in `tools/approvals.py` under the integrator's one-off grant, but the product path was not wired to it. Fix (one place): make `App.resume_approval` claim the row through `ApprovalService.resolve` (or inline its `_claim`, hash check and `decide_on_approve`) and run the follow-up model call only when `executed` is true. After that, rerun A-12b, A-12d, `make eval-attacks` and its replay.

Also noted, not failing: `App.resume_approval` never runs the policy again at approve time (the `decide_on_approve` check exists only in the service), and the service's `taint` argument is caller-supplied with default `low`; contract mode stores no session taint, so "the current taint" at approve time is not observable on either path.
