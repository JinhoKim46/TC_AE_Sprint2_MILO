# M4 requests to the integrator

**Fix cycle 1 update.** `ApprovalService.resolve` (`tools/approvals.py`, one-off M4 ownership) now does items 1 and 2
itself: a compare-and-set claim (`pending` to `approved` once; later resolves answer `already_resolved`) and a
`decide_on_approve` re-run with the stored args and an optional current `taint` (a denial marks the row
`denied_at_approve`, nothing runs). `app.py` only needs `resume_approval` to call the service (M5b integration).
Items 1 and 2 below are otherwise done for the service. The claim is a process-wide lock around the store's
status read and write; a Postgres store needs a real conditional UPDATE (M5-store).

1. **Policy at approve time (answers M3's note).** `App.resume_approval` (`src/milo/app.py`) and
   `ApprovalService.resolve` (`src/milo/tools/approvals.py`) run the bound tool without asking the policy again. The loop
   is the only caller of `decide`, and it runs before the approval row exists, so the policy seam cannot close this
   from inside `security/`. M4 added `decide_on_approve(spec, args, pricing_fields)` to `security/policy.py`: it judges the
   stored call at taint low (an approval row exists only because the policy said `needs_approval` at low) and answers
   `denied` for a missing tool or a tool the policy now denies. Please call it before `tools.call` in both places:
   look up the spec in `tools.specs()`, pass `getattr(tools, "pricing_fields", ())`, and on `denied` set the row to
   `kept`, run nothing and answer with the policy-denied message. Test that will show it works: a `ToolsBackend` whose
   `specs()` no longer lists the tool (or lists it with another risk) after the approval was created; `backend.executed`
   stays empty. Today's defence in depth, which makes the gap low risk: `MiloBackend.call` strips identity keys and
   re-validates the arguments, and the store's owner filter answers `not_found` for another owner's id.
2. **Double approve in parallel (threat-model case A-12b).** `resume_approval` reads the row, checks `status == "pending"`,
   then calls `set_status("approved")`; two threads can both pass the check and both run the tool (two backend
   executions, one state change for a withdrawal). The fix is a compare-and-set on the status (`pending` to `approved`
   succeeds for one caller only) in the approval store (`MemoryApprovals.set_status` or a new `claim`, and the
   `approvals` table in M5-store), used by `resume_approval` and `ApprovalService.resolve`. Not M4's path; M4 did not
   measure it (the attack rows resolve each approval once).
3. **`make eval-attacks`.** The runner defaults to the offline dry mode, so `make eval-attacks` and
   `make eval-attacks-replay` both work without `MILO_LIVE`, and the SPEC 17 M4 done-line ("`make eval-attacks` and its
   replay match") holds as written. The live arm is `run_attacks.py --live` (needs `MILO_LIVE=1`); there is no Makefile
   target for it. Add one if you want, for example `eval-attacks-live` that refuses without `MILO_LIVE=1`, as
   `eval-chat` does. M4 did not touch the Makefile.
4. **Attack rows that exercise the taint rule (M0 or SR).** In `data/attacks.jsonl`, atk04, atk09 and atk10 carry no D22
   phrase, so their taint is low and the approval gate plus the owner filter stop them; atk04's note says "must be denied
   under taint high", which does not happen for that message. No `output_leak` row exists, so the canary check has no
   data (SPEC section 17 M0 says to add one or remove the canary machinery). M4 did not edit `data/`.
5. **Look-alike stripping.** Moved into `security/identity.py` (`strip_lookalikes`, `clean_identity`, `fold_key`).
   `tools/args.py` (M3's path) was edited only to delegate: `clean_args` now returns `clean_identity(raw)`. No change
   for callers. Bare short names (`uid`, `owner`) are deliberately not stripped, so the closed schema rejects them,
   which is what cases A-07a to A-07e expect.
